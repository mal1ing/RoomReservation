# API 설계

## 방 목록 조회

### 요청

GET /api/rooms?date=2026-11-20&attendees=4

인증: 불필요

| 파라미터 | 의미 | 필수 |
|---|---|---|
| date | 이용 날짜, YYYY-MM-DD | 필수 |
| attendees | 이용 인원, 양의 정수 | 필수 |

### 응답 예시

HTTP 200 OK

```json
{
  "items": [
    {
      "id": 1,
      "name": "A룸",
      "description": "화이트보드와 모니터가 있는 공간",
      "capacity": 6,
      "hourly_rate": 10000,
      "currency": "KRW"
    }
  ]
}
```

### 조회 규칙

- 선택한 이용일에 적용되는 정책으로 정원과 요금을 조회한다.
- 정원이 요청 인원 이상인 방을 반환한다.
- 조건에 맞는 방이 없으면 HTTP 200과 빈 items 배열을 반환한다.
- 시간을 지정하지 않았으므로 특정 시간의 예약 가능 여부는 보장하지 않는다.

### 입력 검증

- date는 YYYY-MM-DD 형식의 유효한 날짜여야 한다.
- 과거 날짜는 한국 날짜 기준으로 조회할 수 없다.
- attendees는 1 이상의 정수여야 한다.
- 필수 파라미터가 누락되면 입력 오류를 반환한다.

### 입력 오류 응답 예시

요청: GET /api/rooms?date=2026-11-20&attendees=0

HTTP 422 Unprocessable Content

```json
{
  "detail": [
    {
      "type": "greater_than_equal",
      "loc": ["query", "attendees"],
      "msg": "Input should be greater than or equal to 1",
      "input": "0",
      "ctx": {
        "ge": 1
      }
    }
  ]
}
```

오류 메시지의 세부 표현은 FastAPI·Pydantic 버전에 따라 달라질 수 있다.
프론트엔드는 msg 문자열을 직접 비교하지 않고 loc와 type을 기준으로 안내한다.

## 방 상세 조회

### 요청

GET /api/rooms/1?date=2026-11-20

인증: 불필요

| 파라미터 | 위치 | 의미 |
|---|---|---|
| room_id | 경로 | 조회할 방 ID, 양의 정수 |
| date | 쿼리 | 이용 날짜, YYYY-MM-DD |

### 정상 응답 예시

HTTP 200 OK

```json
{
  "id": 1,
  "name": "A룸",
  "description": "화이트보드와 모니터가 있는 공간",
  "policy": {
    "id": 101,
    "effective_from": "2026-11-01",
    "capacity": 6,
    "hourly_rate": 10000,
    "currency": "KRW",
    "cancellation_notice_minutes": 1440
  }
}
```

### 오류

- 방이 존재하지 않으면 HTTP 404를 반환한다.
- room_id나 date의 형식이 잘못되면 HTTP 422를 반환한다.
- 선택일에 적용할 정책이 없는 경우의 처리는 추후 결정한다.

운영시간·예약 단위·공지 응답은 정책 설계 보완 후 추가한다.

경로: GET /api/rooms/{room_id}
예시: GET /api/rooms/1?date=2026-11-20

## 방 이용 가능 시간 조회

### 요청

경로: GET /api/rooms/{room_id}/availability
예시: GET /api/rooms/1/availability?date=2026-11-20

인증: 불필요

| 파라미터 | 위치 | 의미 | 필수 |
|---|---|---|---|
| room_id | 경로 | 조회할 방 ID, 양의 정수 | 필수 |
| date | 쿼리 | 이용 날짜, YYYY-MM-DD | 필수 |

### 정상 응답 예시

HTTP 200 OK

```json
{
  "room_id": 1,
  "date": "2026-11-20",
  "timezone": "Asia/Seoul",
  "policy_id": 101,
  "slot_minutes": 60,
  "slots": [
    {
      "starts_at": "2026-11-20T09:00:00+09:00",
      "ends_at": "2026-11-20T10:00:00+09:00",
      "available": true
    },
    {
      "starts_at": "2026-11-20T10:00:00+09:00",
      "ends_at": "2026-11-20T11:00:00+09:00",
      "available": false
    }
  ]
}
```

응답의 날짜·정책 ID·예약 단위·시간 블록은 설명용 예시다.
실제 응답에는 해당 이용일의 운영시간 내 블록 전체를 포함한다.

### 조회 규칙

- 선택한 이용일에 적용되는 예약 정책을 사용한다.
- 운영시간 내 블록을 정책의 예약 단위로 나누어 반환한다.
- 확정 예약 또는 유효한 임시 예약과 겹치는 블록은 선택할 수 없다.
- 이미 시작한 블록은 선택할 수 없다.
- 다른 예약자의 이름과 예약 번호는 공개하지 않는다.
- 조회 결과는 해당 시점의 정보이며 예약을 보장하지 않는다.
- 최소·최대 이용 시간과 연속 구간 유효성은 임시 예약 생성 시에도 검증한다.

### 오류

- 존재하지 않는 방은 HTTP 404를 반환한다.
- 잘못된 방 ID 또는 날짜 형식, 필수 파라미터 누락은 HTTP 422를 반환한다.
- 선택일에 적용할 정책이 없는 경우의 처리는 추후 결정한다.

## 임시 예약 생성

### 요청

POST /api/reservations

인증: 필요

```json
{
  "room_id": 1,
  "starts_at": "2026-11-20T14:00:00+09:00",
  "ends_at": "2026-11-20T16:00:00+09:00",
  "attendee_count": 4
}
```

### 처리 규칙

- 예약 회원은 로그인 정보에서 확인한다.
- 이용일에 적용되는 방 정책을 서버에서 조회한다.
- 이용 시간·인원·예약 가능 기간을 검증한다.
- 서버가 정책 요금과 이용 시간으로 최종 금액을 계산한다.
- 같은 방의 확정 예약 및 유효한 임시 예약과 겹치지 않아야 한다.
- 임시 예약 생성 시점부터 기본 5분간 시간을 점유한다.
- 결제 검증 전에는 예약을 확정하지 않는다.

### 정상 응답 예시

HTTP 201 Created

```json
{
  "id": 501,
  "room_id": 1,
  "policy_id": 101,
  "starts_at": "2026-11-20T14:00:00+09:00",
  "ends_at": "2026-11-20T16:00:00+09:00",
  "attendee_count": 4,
  "total_amount": 20000,
  "currency": "KRW",
  "status": "PENDING_PAYMENT",
  "created_at": "2026-11-11T23:30:00+09:00",
  "expires_at": "2026-11-11T23:35:00+09:00"
}
```

날짜·금액·ID는 설명용 예시다.

### 오류

| HTTP 상태 | 상황 |
|---|---|
| 401 | 로그인하지 않았거나 인증이 만료됨 |
| 404 | 방이 존재하지 않음 |
| 409 | 다른 예약과 이용 시간이 겹침 |
| 422 | 입력 형식 또는 이용 시간·인원이 정책에 맞지 않음 |

### 추가 설계 사항

- 중복 클릭·네트워크 재시도로 같은 예약이 여러 건 생성되지 않도록 요청 식별자 기반 중복 방지를 설계한다.
- 화면 조회 이후 정책이나 요금이 바뀐 경우, 결제 전에 변경 내용을 확인받는 절차를 설계한다.
- 업무 오류의 구체적인 응답 본문은 별도로 정의한다.

### 중복 요청 처리 초안

- 요청 헤더에 Idempotency-Key를 필수로 전달한다.
- 프론트는 한 번의 예약 시도에 고유한 키를 생성한다.
- 통신 오류로 같은 요청을 재전송할 때는 같은 키를 사용한다.
- 서버는 로그인 회원과 키의 조합으로 중복을 판별한다.
- 같은 키와 같은 입력이면 기존 처리 결과를 반환한다.
- 같은 키에 다른 입력을 보내면 HTTP 409를 반환한다.
- 같은 키의 요청이 동시에 들어와도 예약은 한 건만 생성한다.
- 키 보관 기간과 처리 중인 재요청의 응답 방식은 추후 결정한다.
